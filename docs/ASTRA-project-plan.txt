# ASTRA

## Astronomical Survey & Transient Research Analyzer

### Final Project Plan

---

# 1. Executive Summary

**ASTRA** is a Windows-first desktop scientific research application designed to discover, investigate, characterize, and prioritize unusual astronomical objects by combining observations from multiple astronomical surveys.

The central idea is not to build another conventional astronomy viewer or another classifier for already-known objects.

ASTRA will focus on:

> **Finding unusual astronomical behavior, combining evidence across independent surveys, determining whether an anomaly is real or an artifact, explaining why it was flagged, and helping researchers decide what should be investigated next.**

The initial platform will combine:

* **ZTF** for time-domain/transient observations
* **Gaia** for astrometry, photometry, and stellar information
* **TESS** for high-cadence time-series observations

The application will run locally on the researcher's machine and use the available **NVIDIA GPU** for accelerated machine learning and scientific computation.

The final product will be distributed as a normal Windows application:

**`ASTRA-Setup.exe`**

Researchers should not need to manually install Python, Node.js, Rust, or the scientific libraries to use the released application.

---

# 2. Core Research Objective

## Primary research question

> Can multimodal, cross-survey astronomical analysis identify scientifically interesting anomalies more effectively than conventional single-survey anomaly detection?

### Secondary research questions

| Research Question                                             | Experimental Approach                                |
| ------------------------------------------------------------- | ---------------------------------------------------- |
| Does combining surveys improve discovery?                     | Compare single-survey and multi-survey models        |
| Can unsupervised systems discover unknown patterns?           | Train without anomaly class labels                   |
| Can the system distinguish artifacts from physical phenomena? | Data-quality and cross-survey consistency analysis   |
| Does multimodal information improve ranking?                  | Compare photometric, astrometric and temporal models |
| Can the system explain anomalies?                             | Feature attribution and evidence generation          |
| Can historical observations increase confidence?              | Temporal cross-survey analysis                       |
| Can the system prioritize scientific follow-up?               | Candidate significance ranking                       |

# 4. What ASTRA Should Actually Discover

ASTRA should not be restricted to a single object class.

Potential discoveries include:

| Candidate Type          | Example Behavior                           |
| ----------------------- | ------------------------------------------ |
| Variable star           | Unexpected periodicity                     |
| Stellar flare           | Unusual flare profile                      |
| Binary system           | Inconsistent eclipse behavior              |
| Transient               | Rare brightness evolution                  |
| Microlensing candidate  | Unusual temporary amplification            |
| AGN                     | Unexpected long-term variability           |
| Stellar interaction     | Unusual multimodal behavior                |
| Moving object           | Unexpected trajectory                      |
| Unknown/rare phenomenon | Does not fit known populations             |
| Instrumental artifact   | Appears anomalous but is not astrophysical |

The application must be capable of concluding:

> **“This is probably an artifact.”**

That is as important as finding a real candidate.

# 13. Anomaly Detection Strategy

ASTRA should use multiple models.

### Baseline models

* Isolation Forest
* Local Outlier Factor
* One-Class SVM
* PCA reconstruction

### Advanced models

* Autoencoder
* Variational Autoencoder
* Transformer-based time-series models
* Contrastive learning
* Multimodal embedding model

### Research principle

Never assume that the newest deep-learning model is automatically best.

The research must compare methods quantitatively.

# 16. Candidate Scoring

Use a composite score rather than a single ML probability.

Example:

| Component                | Weight |
| ------------------------ | -----: |
| Statistical rarity       |    25% |
| Cross-survey consistency |    20% |
| Temporal uniqueness      |    15% |
| Physical inconsistency   |    15% |
| Catalog novelty          |    10% |
| Model agreement          |    10% |
| Data quality             |     5% |

These weights should eventually become experimental variables.

# 17. Explainable Anomaly Report

Every candidate should answer:

### What happened?

### Why was it flagged?

### Which observations support it?

### Could it be an artifact?

### What known objects resemble it?

### What should the researcher do next?

Example:

```text
Candidate: ASTRA-004921

Anomaly score: 0.984

Detected:
• 5.8σ unusual variability
• rare temporal behavior
• cross-survey consistency
• no strong catalog classification

Potential explanations:
1. Rare stellar variability
2. Binary interaction
3. Transient phenomenon
4. Instrumental artifact

Recommended action:
Review historical observations and consider spectroscopic follow-up.
```

Do not begin with the entire astronomical archive.

### Stage B

Medium-scale datasets for algorithm testing.

Full-scale discovery campaigns.

# 36. Important Research Controls

ASTRA must explicitly handle:

### Selection bias

The system should document how candidates enter the pipeline.

### Data leakage

Training and evaluation data must be separated correctly.

### Survey bias

Different instruments have different sensitivities and observational patterns.

### Instrumental artifacts

An anomaly should not automatically be considered astrophysical.

### Class imbalance

Rare astronomical events will be highly imbalanced.

### Uncertainty

The system should report uncertainty rather than pretending every prediction is certain.

# 42. Final Recommendation

The project should be built with three clearly separated layers:

### Layer 1 — Desktop

**Tauri + Rust + React + TypeScript**

Responsible for:

* interface
* files
* application lifecycle
* hardware detection
* user interaction

### Layer 2 — Scientific Engine

**Python + Astropy + Astroquery + Lightkurve + NumPy + SciPy + Polars + Dask**

Responsible for:

* astronomical calculations
* data ingestion
* preprocessing
* feature extraction
* cross-survey analysis

### Layer 3 — Intelligence

**PyTorch + scikit-learn + CUDA + CuPy + C++ where necessary**

Responsible for:

* anomaly detection
* multimodal representation
* candidate ranking
* pattern discovery
* GPU acceleration

This separation keeps ASTRA maintainable while allowing each technology to do what it is best at.
